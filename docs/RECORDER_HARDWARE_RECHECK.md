# Recorder 硬件回归对照复测

日期：2026-09-16。基准：改动前 `e4145bf`；故障版本：`da50b56`。

## 结论与更正

原版 recorder 能连接四臂、读取所需反馈、回零和执行 J6 ±45° 预定位。
同一环境紧接着运行 `da50b56`，两主臂均在初始回零时报告“切换 follower 后没有关节反馈”。
这是本次改造新增的反馈判定造成的软件回归，不能将回零失败简单归因于硬件。

按用户要求，完整撤回 `scripts/PiperRecorder/piper_recorder/robot.py` 的全部修改，
恢复 `e4145bf` 原文件，包含模式切换、反馈获取、CAN 预检、运动、回零同步、限幅及异常处理。
恢复后 SHA-256：`514a9b19d3177f4276559644caf613b1ce07d638ed70d3c77dd0685c99c901d5`。
后续 Web 集成继续调用原有硬件流程，不自行增加 SDK 反馈或运动判定。

部署桥也撤回了“预定位失败时额外自动回零”的改动，恢复原版动作及回零清理注册顺序。
其连接、预定位、回零、读取状态和控制循环的函数/类 AST 与基准一致。
保留 Web 包装、进程互斥、Socket 资源清理及非硬件控制的参数校验。

## 实测过程

1. 从 Git 提取原版 recorder 到 `/tmp/easy-recorder-ab-e4145bf/`，校验入口和 robot.py 与基准一致；使用相同的现有 piper-home 环境、SDK 和原默认参数。
2. 原版实际运行：三路相机、四臂连接、示教器响应、初始四臂/夹爪回零、J6 左 −45°/右 +45°、200 Hz 跟随启动均通过；输入回车结束，四臂/夹爪再次回零，输入 `:q` 后退出码 0。
3. 故障版本实际运行：相机与四臂连接通过，初始回零时两个主臂均超时，退出码 1。此时四路 CAN 都为 ERROR-ACTIVE。
4. 临时诊断程序只切模式并记录时间戳，不发送关节运动目标：每 50 ms 重发 follower 配置期间，主臂反馈间歇更新，左、右主臂最长均只有两次连续的新反馈；停止重发后，后续采样恢复连续更新。
5. 单独恢复原版“一份新反馈即结束切换”的逻辑后，终端初始四臂/夹爪回零通过。
6. 按用户指示进一步恢复整个原版 robot.py；通过现有统一 Web 的真实 API 完成启动、初始回零、指令、J6 预定位、跟随、结束、回零与正常退出，退出码 0。

本次无人进行示教动作。原版和恢复后的 Web 均按原逻辑拒绝保存没有 task 帧的空任务，
测试没有生成训练数据，也没有改动原采样阈值去绕过该要求。
最终四臂及夹爪均由原版回零流程确认到位，设备连接已关闭。

## 原因

原版重复发送模式请求，收到比切换前更新的关节反馈就返回。
改造版把条件改为“连续三次轮询都取得更新反馈”，同时继续每 50 ms 发送模式请求；
真实固件在反复配置期间的反馈时序无法稳定满足这个新条件，从而一直等待到超时。
异常文本“没有关节反馈”也掩盖了实际存在间歇反馈的事实。
最初的模拟测试只验证了人为设定的连续反馈序列，没有覆盖真实固件时序，未能发现该回归。

此前 ERROR-PASSIVE 是首次测试中的真实观测，但其具体诱因没有确认。
本次不重启 CAN、不改 SDK、不修改设备映射，A/B 结果已足以定位上述软件回归。
